# 日语视频同声传译（字幕版）完整方案

> 目标：看日语视频时，屏幕上实时出现「日文原句 + 中文译文」双语字幕。
> 状态：**已在本机跑通并有实测数据**，全离线、不需要联网、不需要虚拟声卡。
> 适用机器：Windows 10/11 + NVIDIA 显卡（本机 RTX 4060 Laptop 8GB）。

---

## 一、一句话结论

**本地方案已经完全够用，不需要买任何云端服务。**

链路只有四步，每一步都有更省事的替代品，但这一套是「准确率 / 延迟 / 显存」三者平衡最好的：

```
系统声音（WASAPI 回环，免虚拟声卡）
   → Silero VAD 按停顿切成整句
   → ReazonSpeech 日语模型转文字（int8，155MB，CPU 跑，39 倍实时）
   → 本地大模型翻成中文（ollama，0.3–1.2 秒）
   → 屏幕底部置顶悬浮字幕
```

实测：一句话说完后 **约 0.5–1.4 秒**出译文，显存占用约 6.6GB（只有翻译模型吃显存）。

## 二、三条路线怎么选

| 路线 | 延迟 | 准确率 | 成本 | 隐私 | 适合谁 |
|---|---|---|---|---|---|
| **① 本地自建（本方案，已跑通）** | 句末 +0.5~1.4s | 日译英/中接近可用 | 0 元 | 全离线 | 想省钱、能接受一点点延迟 |
| ② 云端实时同传 API | 字均 2.3s（阿里 Qwen3.8-LiveTranslate） | 最好，还带情绪/说话人 | 按分钟计费 | 音频上传 | 追直播、会议，要求译文质量最高 |
| ③ 现成软件 AudioScript 声稿 | 句末 +0.8~8s | 中（ja 从未被验证） | 0 元 | 全离线 | 不想折腾，装完就用 |

**给你的建议：先用 ①**。它已经跑通了，免费、离线、延迟可控。真遇到听不懂的术语再考虑 ②。

> ② 的细节：阿里百炼 `qwen3.8-livetranslate-flash-realtime`，端到端视听同传，音频+画面一起喂，
> 60 语种互译。设 `session.output_modalities=["text"]` 就只出译文——正好符合你「只要字幕不要配音」。
> 但权重不开放，没法本地跑。
> ③ 的细节：github.com/niyongsheng/AudioScript（MIT，Tauri+Rust）。Windows 用 WASAPI 回环抓声音，
> 界面比本方案完善（有历史记录、导出）。缺点是日译中这条路径**代码放行但从未验证过**，
> 而且它把日语识别当离线模型用，只出 final，默认句子最长 8 秒 → 译文滞后比较多。

## 三、为什么是这几个模型（选型依据，都是查过一手资料的）

### 3.1 日语识别：ReazonSpeech k2-v2 而不是 Whisper

| 模型 | JSUT CER | CV8 CER | TEDxJP-10K CER | 体积 |
|---|---|---|---|---|
| **ReazonSpeech k2-v2** | **6.45** | **7.85** | **9.09** | int8 约 155MB |
| Whisper large-v3 | 7.18 | 8.18 | 9.96 | 约 3GB |
| ESPnet | 6.89 | 8.27 | 9.28 | — |

（以上为 ReazonSpeech 官方基准，同源可比）

**决定性理由不是这几个小数点，而是幻觉。** Whisper 系有结构性的「给静音补一句话」问题：
公开论文实测整体约 **1%** 的转写整句是凭空编的，**非语音片段平均幻觉率 31.31%**，
而且静音占比越高越严重。看视频时大量片段是纯音乐、无人声——用 Whisper 会不停蹦出根本不存在的字幕。
ReazonSpeech 是 transducer 结构，解码不是生成式的，**结构上就没有这个机制**。

代价：**它不带标点**。不过中文译文天然带标点，所以这个缺点在字幕场景里被翻译环节消化掉了。

### 3.2 翻译：本地小 LLM 而不是传统 NMT

实测证据（koe-bridge，FLEURS，RTX 3060）：小 NMT 在日英上 **BLEU = 0.0**，
输出通顺但内容和原文无关；更致命的是**整句翻译会丢掉否定标记 22–25%**
（"He did not set a figure" 翻成肯定句）——对字幕是硬伤。

所以用 LLM。本机现成的是 `qwen3.5:latest`（9B，Q4_K_M，6.6GB）。

**必须注意的两个参数**（不设就是坑）：
- `num_ctx=2048`：默认 262144 会把上下文开满，实测吃 20GB 内存、79% CPU 推理，直接把机器拖死
- `think:false`：否则模型只输出思考过程，`content` 为空

想更省显存可以换 `qwen2.5:1.5b` 之类（质量会降），显存能从 6.6GB 掉到 1GB 出头。

### 3.3 为什么不逐字流式翻译

日语句子是 **SOV 结构**，动词和否定全在句尾。这意味着「看到半句就翻」必然翻错、而且会被反复推翻：
- 同一后端下，前缀存活率（读到 50% 处的译文有多少能活到句末）**英译日 0.014，日译英 0.184，差 13 倍**
- 否定极性在读到 10% 时，**约 0.7 的概率会翻错**，要读到 30% 才第一次给对

所以主线必须是 **VAD 整句翻译**。逐字流式（LocalAgreement-2 那套）只用在 ASR 侧的局部一致性，
不用在翻译侧。这是本方案最核心的设计决策，不是偷懒。

## 五、踩过的三个坑（这部分最值钱，别重复踩）

### 坑 1：从句中切出来的片段，识别器会把开头几个词吞掉

现象：完整文件转录完美，但按停顿切开后，第一段只剩尾巴。

```
整段 6.62s        → はやくおじいさんにあのおとこのはなしをきかせたかったのです   ✅
从 0.93s 切 1.15s → じいさん                                                    ❌
从 0.93s 切 3.45s → いかせたかったのです                                        ❌
```

原因：transducer 编码器的首个 chunk 没有左上下文，从语音中间起头就会解码跑偏。

**修复**：每个片段送进识别器前 **补 0.5 秒前置静音**。加完立刻正确：

```
seg1 + 0.1s 静音  → 早くおじいさん
seg1 + 0.3s 静音  → 早くおじいさんに
合并 + 0.5s 静音  → はやくおじいさんにあのおとこのはなしをきかせたかったのです   ✅
```

代码里就是 `_process()` 开头那一行 `np.zeros(SR//2)` 拼接。**这不是调参，是正确性问题。**

### 坑 2：`vad.pop()` 会让 `vad.front` 返回的段落立刻失效

```python
seg = vad.front
vad.pop()
len(seg.samples)    # → 0，读到的是空的
```
必须先 `np.asarray(seg.samples).copy()` 把样本取出来，再 pop。否则所有段落都被
`if len(samples) < SR*0.2: continue` 过滤掉，表现为「跑得飞快但一句话都不出」。

### 坑 3：这台机器的 pip 和 uv 都是坏的

- `pip install --target` 一律 `PermissionError: [Errno 13] ...whl.metadata`
- `uv` 报 `Failed to inspect Python interpreter ... os error 5 拒绝访问`（子进程 python.exe 被拒）
- venv 建出来没有 pip（ensurepip 同样 WinError 5）

**唯一可行办法**：PyPI JSON API 拿 wheel URL 直接下，`zipfile.extractall(libs)` 解压，靠 `sys.path` 使用。
`sherpa-onnx-core` **必须显式挑 `py3-none-win_amd64`**，自动匹配会装成 `android_24_arm64_v8a`——
导入不报错，一跑就崩。

## 五之二、真机联调又抓出的四个问题

前三坑是离线测试阶段发现的，下面这四个只有真正接上 B 站视频、从 `start.bat` 双击启动才暴露。

### 坑 4：UTF-8 编码的 .bat 在 cmd 里根本跑不起来

双击 start.bat，屏幕一闪就没了，报：

```
'放视频即?echo' 不是内部或外部命令
']' 不是内部或外部命令
```

原因：**cmd 按系统 ANSI 代码页（GBK）解析 .bat 文件**。文件是 UTF-8 存的，中文字节在解析阶段
把换行吃掉，`echo` 和后面几行被拼成一条不存在的命令。`chcp 65001` 只影响**控制台输出**编码，
救不了**文件解析**阶段的解码。

修法：**bat 里一个中文字符都不能有**，全改英文。中文只出现在 Python 程序里（那边有 UTF-8 兜底）。

### 坑 5：翻译模型会自作聪明补一句「（此处需补充完整句子）」

小模型遇到不完整的日语片段，会写这种元话语，直接上屏根本没法看。

修法两道：提示词明确「原文残缺就直接翻，不许写补充说明」；再加一层正则清洗——
只清掉含 `补充/此处/原文/未完/无法…` 这些词的括号块，正常的「（笑）」不受影响。

### 坑 6：汉字数字被翻错量级

`およそ百億円` 被翻成「1000 亿日元」，而且三跑两次错。提示词加「数字必须严格一致」也没压住——
小模型对「百億」这种汉字数量级的理解本身就不稳。

修法：**在送翻译之前先把汉字数字转成阿拉伯数字**，`百億 → 100億`、`千億 → 1000億`、`十億 → 10億`、
全角数字也一并转半角。改完三跑三对。

### 坑 7：快语速连续对话会被并成十几秒一段

VAD 靠 0.35s 停顿切句，但动画对话里停顿常常短于这个值，于是整段连续并起来——
实测出现过 **13.1 秒**一段，观众都看丢了才出字幕。

修法：**不靠 VAD 硬截**（硬截会丢音频，见 `--max-speech` 那条），而是拿到整段后在**能量低谷处切块**，
每块不超过 6.5 秒。音频一个采样都不丢，切开后靠「补前置静音」保证每块仍能认对：

```
13.1s 一段 → 3.6s「H二Aは打ち上げの成功率は高い一方」
           + 6.0s「一回の打ち上げ費用がおよそ百億円と…」   两段都完整正确
```

配套还有一条兜底：攒着的半句如果后面超过 4 秒没声音，就放出来，不能无限等下一句。
这个阈值不能设太小——实测 2.0 秒会在下一句开口前就把「気象庁」单独放掉，半句照样碎。

## 六、怎么跑

### 6.1 直接启动

双击 `start.bat`，或命令行：

```bash
cd "D:\DeepSeek Harness\ja-subs"
.venv\Scripts\python.exe live_ja.py
```

然后正常打开视频。字幕会浮在屏幕底部。

**字幕条怎么调、怎么关**（都可以用鼠标完成，不用记快捷键）：

| 操作 | 效果 |
|---|---|
| 鼠标左键拖动 | 移动字幕条位置 |
| **滚轮上下** | 调字号（12–44，实时生效，框高自动跟着变） |
| **Ctrl + 滚轮** | 调字幕条宽度（屏宽的 30%–98%） |
| **右键** | 弹出菜单：字号 ±、宽度 ±、更透明 / 更不透明、**退出** |
| **点右上角 ✕** | 关闭 |
| 双击 `start.bat` 的窗口按 Ctrl+C | 也可以关 |

> 为什么不靠 Esc：这个窗口是 `overrideredirect` 的置顶窗，Windows 不会把键盘焦点给它，`bind("<Escape>")` 实际上永远收不到按键——之前"找不到怎么关"就是这个原因。现在 ✕ 和右键菜单都是纯鼠标路径，不依赖焦点。
>
> 框是**固定宽度 + 高度自适应**的：短句不会缩成一条，长句会自动撑高，不会再出现文字被截断或留一大片空白。

### 6.2 常用参数

```bash
# 列出声卡，确认回环设备在不在
python live_ja.py --list

# 抓错设备时手动指定（名字关键字就行）
python live_ja.py --device Realtek

# 顺便存一份双语字幕文件
python live_ja.py --srt 我的字幕.srt

# 不要悬浮窗，只在控制台看
python live_ja.py --no-gui

# 用音频文件离线跑（不抓声音，用来验证环境）
python live_ja.py --file model_ja/1.wav --no-gui

# 看本机装了哪些翻译模型
python live_ja.py --models

# 换小模型（省显存、更快，但会更不准，见 6.4）
python live_ja.py --model qwen2.5:3b

# 嫌字幕太大 / 太宽，直接给初值
python live_ja.py --font 18 --width 0.6 --alpha 0.9
```

### 6.3 调参

| 参数 | 默认 | 说明 |
|---|---|---|
| `--min-silence` | 0.35 | 停顿多久算一句结束。**调大**（0.6~0.8）整句更长、译文更连贯，但延迟变大；**调小**（0.2）反应快但容易切碎 |
| `--max-speech` | 15.0 | 单句上限。**不要调到 4 以下**——实测强制截断会丢音频（4 秒上限时 13.4 秒音频丢了 2.1 秒，中间"暴風雪や高波に警戒"整段消失） |

调参顺序建议：先默认跑，觉得碎就加 `--min-silence 0.5`，觉得慢就降到 `0.25`。

### 6.4 换翻译模型（小模型到底行不行，用数据说话）

翻译模型是插拔的，`--model 模型名` 就能换，`--models` 看本机有哪些。我实测了两个（同一批 6 句，含数字、专有名词、敬语）：

| 模型 | 磁盘 | 显存 | 每句延迟（中位） | 结果 |
|---|---|---|---|---|
| `qwen3.5:latest`（默认） | 6.6 GB | **5.5 GB** | 0.41 s | 6/6 正确 |
| `qwen2.5:3b` | 1.9 GB | **2.1 GB** | 0.17 s | 有明显错译 |

3B 具体错在哪（这些都是真实输出，不是我编的）：

| 原文 | 9B | 3B |
|---|---|---|
| 一回の**打ち上げ**費用がおよそ100億円 | 单次**发射**费用约 100 亿日元 | **一場的宴会**费用约 100 亿**円** |
| よろしくお願いしますね | 请多关照 | 你好，麻烦你了 |
| 早くおじいさんに…きかせたかった | 早就想给爷爷讲讲… | 我真想早点…（改提示词前这句是「我 **really** 想…」） |

所以：

- **不缺显存就用默认 9B**。3B 省下 3.4GB 显存、每句快 0.24 秒，但字幕里出现「宴会」这种错译，比慢半秒难看得多——而且 0.4 秒本来就不是瓶颈（瓶颈是等一句话说完）。
- **要一边开游戏/剪视频**、或者显存被别的程序占了，再用 `--model qwen2.5:3b`。它至少语句通顺、数字不会凭空加零，能看。
- 术语密集的内容（动画专有名词、技术直播）在 3B 上错得更频繁，别硬用。

想再要一个中间档可以自己拉：`ollama pull qwen2.5:7b`（约 4.7GB），介于两者之间，我没实测就不写结论。

## 七、局限与已知问题（不粉饰）

1. **普通句子仍要等句末，连续长句改为中途切段。** 这是整句翻译的固有代价。VAD 当前语音段连续达到约 5 秒时，会复制当前段并重置 VAD，后续音频无重叠继续；最坏大约是「5 秒语音 + 1–2 秒识别翻译」后上屏。切点偶尔会落在词中间，译文可能略碎，但不会再等十几秒后一次性蹦出多段。可用 `--long-cut` 调大或调小。
2. **标点靠译文补。** 日文原句那一行永远没有标点，中文那行有。
3. **`最大句长`不能设太小**，见坑 3 的音频丢失问题。
4. **数字/专名偶尔汉字化**：`H2A` → `H二A`、`１８歳` → `十八歳`。翻译环节一般能纠正（实测正确输出 H-IIA），但偶尔会漏。
5. **显存吃紧**：9B Q4 常驻 5.5GB / 8GB，同时开游戏或剪视频会不够。换 3B 只占 2.1GB，但错译明显增加——取舍见 6.4。
6. **锁死的目录还在**：`models/sherpa-onnx-zipformer-ja-reazonspeech-2024-08-01` 因为 Windows 权限问题读不了也删不掉（是一次解压事故留下的）。实际用的是 `model_ja/`，那个目录留着无害，想清理需要资源管理器管理员权限手动删。
7. **没有标点恢复、没有说话人分离、没有术语表注入**——这些云端方案有，本地这套没有。
8. **双声道分流只处理标准双声道。** 左右内容不同时显示“左/右”两行；内容相同会自动去重。五声道、7.1 等布局目前回退到整轨混合单声道。

## 八、英语怎么办

同一套管道，换掉两个模型就行：

| 环节 | 日语（现在） | 英语 |
|---|---|---|
| 识别 | ReazonSpeech k2-v2 int8 | sherpa-onnx 的 `zipformer-en` 系列，或 Whisper turbo |
| 翻译 | qwen3.5:9B（中英都能翻） | 不用换 |

英语比日语简单：Whisper 系列在英语上的幻觉率远低于非英语，而且英语是 SVO 结构，
动词在句中，**逐字流式翻译在英语上反而可行**——想更快可以给英语单独开一条流式通道。

语言码在 `live_ja.py` 里的 `MT_SYS` 提示词里，改一句就行。

## 九、如果哪天想要更好的效果

按性价比排序：

1. **换翻译模型**：`qwen3.5:9B` → 更大的模型（如果显存够）。翻译质量是整条链路现在的短板，不是识别。
2. **换识别模型**：`Qwen3-ASR-0.6B`（11.89% CER，能喂专有名词、带 BGM 也能识），代价是 600MB 且长音频必须切段。
3. **上云端**：阿里 Qwen3.8-LiveTranslate，字均 2.3 秒延迟、视听联合、带说话人分离和声音复刻。要花钱，但准确率是另一个档次。

## 九之二、浏览器插件版（原型，`ext/`）

不想让它抓「整个系统的声音」，而是只抓某个标签页、还能在页面里开关和切字幕模式，就得上插件。

**架构**（和桌面版共用同一套模型，只是换了收音频的入口）：

```
Edge/Chrome 扩展
  popup 点击「开启」
    → background.js: chrome.tabCapture.getMediaStreamId({targetTabId})
    → offscreen 文档: getUserMedia({chromeMediaSource:'tab'}) 拿 MediaStream
    → AudioContext 48000Hz → 线性插值降到 16k → Int16 PCM
    → WebSocket ws://127.0.0.1:8765  （二进制帧）
本地服务 server_ws.py
    → VAD 切句 → ReazonSpeech 识别 → qwen3.5 翻译
    → 文本帧回 {"ja":..., "zh":...}
content.js
    → Shadow DOM 字幕条，贴在最大那个 <video> 上，全屏自动挂进全屏元素
```

**为什么必须有个本地服务**：识别（776MB）+ 翻译（6.6GB）跑不进浏览器。sherpa-onnx 有 WASM 版，日语模型塞进浏览器也能跑，但翻译模型没有可行方案，拆开只是把问题挪个地方。

**几个必须知道的点**：

1. **捕获后会静音**。`getUserMedia` 拿到 tab 音频后，这个标签页自己就没声了；必须把 `MediaStreamSource` 再接一次 `ctx.destination`，否则用户看视频没声音。`offscreen.js` 里已经接了。
2. **「内嵌到视频里」的真相**：浏览器插件**无法**把字幕真正烧进视频画面（那需要重新编码）。能做的是把字幕条按 `<video>` 的 `getBoundingClientRect()` 贴合上去，看起来像嵌在视频里，全屏也跟得上。想真烧进画面只能用 ffmpeg 重新压一遍，那就不是"实时看"了。
3. **全屏会消失**：全屏时浏览器只显示全屏元素及其子孙，所以字幕条必须 `appendChild` 进 `document.fullscreenElement`，否则一按全屏字幕就没了（`content.js` 已处理）。
4. **DRM 站点**（Netflix 等）可能拿不到音频或被限制，没验证，别当承诺。

**装法**：`edge://extensions` → 打开「开发人员模式」→「加载解压缩的扩展」→ 选 `ext` 文件夹。先双击 `start-server.bat` 起服务，再在视频页点插件图标 → 开启字幕。

### 点一下按钮就自动起服务（可选，推荐）

默认要手动开个黑窗口才能用，麻烦。改成自动：

```
点「开启字幕」
  → chrome.runtime.connectNative('com.jasubs.launcher')
  → 浏览器启动 native/ja_host.exe（C# 写的转发器）
  → ja_host.exe 检查 127.0.0.1:8765
       已在跑 → 直接返回 {"already":true}
       没在跑 → CreateProcess 拉起 .venv\Scripts\pythonw.exe server_ws.py
                （CREATE_NO_WINDOW + CREATE_BREAKAWAY_FROM_JOB，无窗口、不继承浏览器进程树）
  → 插件重试连 WS（最多 60 秒，等模型加载完）
```

**为什么要注册表**：浏览器出于安全**不可能**直接启动本地程序，唯一合法通道是 native messaging，而它要求在注册表登记宿主清单。登记一次就永久有效。

**装法**：双击 `setup-native.bat`（内部跑 `native/register.ps1`，会从浏览器配置里读出扩展的真实 ID 再写注册表）。
**这一步必须由你双击**——我的进程跑在受限沙箱里，写 HKCU 被拒绝。

**副作用与处理**：

- 黑窗口没有了，日志改到 `logs/server.log`（`pythonw` 没有控制台，stdout 被重定向过去）。
- 服务空闲 30 分钟没有插件连接会自己退出，不长期占显存；想早点退就关掉字幕再等一会儿。
- 重复点击不会起第二份模型：`server_ws.py` 启动时先探测端口，已在跑就直接退出。
- `start-server.bat` 保留，调试时手动起仍可用；此时插件点开启会直接连上，不会再拉一份。

### 字幕样式与翻译模型切换（2026-11-04 增补）

插件弹窗里「更多设置」默认展开，可调：

| 项目 | 选项 | 说明 |
|---|---|---|
| 显示 | 原文+译文 / 只看译文 / 只看原文 | 和之前一样 |
| 字幕大小 | 小 16 / 中 22 / 大 28 / 特大 34（px） | 日文行自动按 0.6 倍缩 |
| 字幕颜色 | 白 / 黄 / 青 / 绿 / 粉 | 只改译文，原文固定淡蓝 |
| 描边方式 | 无 / 细 / 粗 | CSS text-shadow 三层堆叠，浅色画面上可读 |
| 默认位置 | 贴近进度条 7.5% / 画面中下 14% / 偏上 25% | 按视频高度百分比，不是固定像素，换分辨率不跑位 |
| 背景透明 | 0–100% 滑块 | 对应字幕条背景 alpha |
| 淡入淡出 | 开关 | 每句用 Web Animations 做 220ms 淡入 |
| 等比缩放 | 开关 | 字号跟着视频宽度走（1280 宽为基准，0.55–1.6 倍），小窗播放时字不会过大 |
| 翻译模型 | 标准 qwen3.5 9B / 轻量 qwen2.5 3B | 默认 9B，切换即时生效 |

**改动即时生效**：所有选项写 `chrome.storage.local`，`content.js` 用 `storage.onChanged` 监听，拖滑块字幕框当场变，不用重开字幕。

**字幕上的 ✕ 去掉了**：以前挂了个 ✕，但它是 `pointer-events` 唯一要开的口子，会把视频这块区域变成死区（挡住进度条、双击全屏）。现在整条字幕 `pointer-events:none`，鼠标穿透，关闭统一走插件按钮。

**模型怎么切**：`offscreen.js` 在 WS 连上时和 `storage.onChanged` 时发 `{"cmd":"model","name":"..."}`，服务端白名单校验后改 `live_ja.MT_MODEL` 并异步预热，回 `{"type":"model","ok":true}`。白名单只有那两个名字，非法值直接 `ok:false` 拒掉（防止任意字符串被塞进 ollama 请求）。切换时 ollama 要换显存里的模型，第一句会慢 3–5 秒，之后恢复正常。

实测（`tests/test_model_switch.py`，同一段 1.wav）：

```
→ 切 3B 回执：{'type': 'model', 'ok': True, 'name': 'qwen2.5:3b'}（3.34s）
  [5.0s] 気象庁は雪や路面の凍結による交通への影響 → 气象厅对雪和路面结冰对交通的影响
  [5.3s] 暴風雪や高波に警戒するとともに        → 同时警惕暴风雪和巨浪
  [5.7s] 雪崩や屋根からの落雪にも十分注意するよう呼びかけています → 呼吁人们要充分注意雪崩和屋顶上的落雪
→ 切回 9B 回执：0.00s
→ 非法模型回执：{'type': 'model', 'ok': False, 'name': 'rm -rf /'}
```

3B 这三句都对，但它在基准句上出过「打ち上げ→宴会」这种硬错（见 6.4），所以默认仍然是 9B。

## 九之三、插件改走「回环采集 + HTTP 轮询」（2026-11-04 晚，v0.6.0）

原先是 `tabCapture → offscreen 文档 → WebSocket` 三段链路。实测下来 offscreen 文档是最大的不稳定源：
扩展重载后旧文档仍活着、跑旧 JS，新代码永远等不到音频，日志里只看到「连上就断开」。

现在改成：

| 环节 | 谁做 | 说明 |
|---|---|---|
| 采音 | 本地 Python 服务（`server_ws.py --loopback`） | 直接抓系统回环，等于「你在放什么就抓什么」 |
| 识别 + 翻译 | 同一个服务进程 | 结果写进内存队列 `SUBS` |
| 显示 | 页面里的 `content.js` | 每 300ms `GET /subs?since=N`，不用 WS、不用 offscreen |
| 开关 | 插件 popup | 开启=拉起服务并注入脚本；关闭=`GET /quit` 让服务退出 |

为什么这样更稳：`content.js` 每次点开启都由 `chrome.scripting.executeScript` 重新注入，永远是磁盘上最新那份；
而 offscreen 文档的生命周期不受控，已被反复证明会跑旧代码。少一个组件，少一类故障。

代价：抓的是整机声音，不是单标签页（所以别的软件出声也会被识别）。对「看视频」这个场景够用。

配套改动：

- `native/Launcher.cs` 拉起服务时加 `--loopback` 参数；
- 关闭字幕会 `GET /quit`，服务进程退出，**显存和内存立刻还回去**（之前关掉字幕显存仍被占着就是这里没做）；
- 服务自己抓音，`L.Pipeline` 的构建放到工作线程里，避免卡住 4 秒事件循环（这个坑也修了）。

自测结论（本机实测）：`tests/test_loopback.py` 外放 `model_ja/2.wav`，6.1 秒出字幕
「早くおじいさんにあの男の話を聞かせたかったのです」→「我想快点把爷爷讲那个男人的事。」

## 九之四、延迟到底花在哪（2026-11-04 晚，v0.6.2）

先把账算清楚，别拿「感觉慢」调参。用 `tests/bench_pipe.py` 按实时速度把 wav 喂进管线，
量的是**句末时刻 → 字幕上屏**的差（不含抓音设备抖动）：

| 版本 | 句末→上屏（1.wav，3 句） | 现象 |
|---|---|---|
| 改之前（feed 里同步翻译） | 9.41 / 6.50 / 2.46 秒 | 越往后越快，因为采集一直在丢音追不上 |
| 改之后（翻译挪到工作线程） | **1.74 / 1.01 / 1.24 秒** | 译文完整，`data discontinuity` 警告消失 |

**真正的病根不是模型慢**：ASR 只要 73–151ms，翻译 519–862ms。是 `feed()` 里同步调
`translate()` 把采集线程卡住了——soundcard 缓冲区一满就丢样本，日志里那堆
`data discontinuity in recording` 就是在丢音。丢音又导致两句之间接不上，
「暴風雪や高波」被切掉、认出「工事」这种错字。**延迟和错字是同一个原因**。

修法：`feed()` 只做 VAD 切句并丢进队列（`queue.Queue(maxsize=8)`），
`_work_loop()` 线程里跑 ASR + 翻译；队列满了宁可丢最旧的整段，也绝不阻塞采集。

那 1 秒的剩余延迟由这几块构成：VAD 静音判定 0.35s + ASR 0.1s + 翻译 0.5–0.9s + 轮询 0.15s。

**试过又回退的**（记下来免得以后再踩）：

- `min_silence` 0.35 → 0.28：把「気象庁は」这种半句切出来，单翻成「气象厅是」，纯噪音；
- 短句合并阈值 2.2s → 1.2s：同上，残句变多；
- 长段切块 6.5s → 4.0s：切点落在词中间，`暴風雪` 被认成 `高圧`；
- 「以助词结尾就攒着」的启发式：反而把 `気象庁は…交通への影響` 粘成一段再造出「工事」。

参数已经回到实测最优（0.35 / 2.2s / 4.0s 兜底 / 6.5s 切块），只保留零代价的那项：页面轮询 300ms → 150ms。

**还剩的结构性延迟**：一句不停顿的长话（新闻播报那种 10 秒一口气）要等它说完才切块，
最坏 ≈6.5 秒后才上屏。这不是参数问题——VAD 只有听到停顿才知道句子结束。
真要解决得上流式 ASR + 增量翻译，代价是译文会来回改（日语 SOV 语序决定了前缀翻译必被推翻，
实测前缀存活率 0.014），对看动画反而是负体验。

**「能不能直接拿音频层」**：不能。浏览器不把 `<video>` 的音轨暴露给扩展；
页面内 `createMediaElementSource` 只有页面自己的 JS 能接，content script 跨隔离世界拿不到，
而且接了会改变页面音频输出。就算拿到也不会更快——瓶颈是「等句子说完 + 翻译」，
不是采集。`tabCapture` 能拿标签页音频（我们之前那套），延迟一模一样，只是能少抓别的软件的声音。

## 十一、桌面版 exe：不依赖浏览器，任何软件都能用（2026-11-04 增补）

### 11.1 为什么「换软件」根本不用改代码

抓音用的是 **WASAPI 回环（loopback）**：拿到的是「送往某个输出设备的音频数据流」，
跟哪一个进程在放、放的是浏览器还是 PotPlayer 完全没有关系。
所以 Telegram、PotPlayer、B 站客户端、本地播放器，只要是这台机器在出声，就都能翻。

浏览器插件那套只是**显示层**（把字画在网页上）；换成桌面 exe，显示层换成 tkinter 置顶悬浮窗，
识别翻译完全是同一套代码（`live_ja.py`），一个字节都没换。

### 11.2 一定要外放吗？耳机行不行？

**不需要外放，也不用麦克风。** 回环取的是混音后的数据流，不是空气里的声音：

- 不外放、只插耳机：行（耳机就是当时的默认输出设备，回环跟着它走）；
- 音量拉到 0 或设备静音：照样能抓（静音作用在端点输出端，不影响回环数据）；
- 实测证据：把音频送到一个**完全虚拟、没有任何扬声器**的设备（Steam Streaming Speakers，
  而且它不是默认设备），从它的回环里录到峰值 **0.2960**——要是靠"听声音"，这里应该是 0。

**唯一要注意的是「切设备」**：原来代码在启动时抓死一个设备，中途插耳机就永远收不到声音。
现在 `capture_loopback(follow=True)` 每约 2 秒检查一次默认输出设备，变了就自动重连
（日志里会打「输出设备已切换到「XXX」，重连录音」）。

抓不到的情况（这是 WASAPI 的限制，不是本方案的 bug）：

| 场景 | 能不能抓 | 说明 |
|---|---|---|
| 3.5mm / USB-C 耳机 | ✅ | 插上即成为默认输出，自动跟随 |
| 蓝牙耳机（A2DP） | ✅ 多数可用 | 少数驱动不暴露回环；偶发时钟抖动会有 `data discontinuity` |
| 播放器开了 **WASAPI 独占模式** | ❌ | 独占端点时 loopback 拿不到数据 |
| 播放器走 **ASIO**（如 foobar2000 ASIO） | ❌ | 绕过 Windows 混音器，回环看不到 |

### 11.3 JaSubs.exe

`D:\DeepSeek Harness\ja-subs\JaSubs.exe`（C# WinForms，40KB，csc 编译，带图标 `ja.ico`）：

- 双击出一个小窗，点「开始字幕」→ 拉起 `python live_ja.py` → 屏幕上出现字幕条；
- 面板上的设置会翻译成命令行参数传给 `live_ja.py`，改完**重新点「开始字幕」**生效：

| 面板项 | 参数 | 可选值 |
|---|---|---|
| 字号 | `--font` | 12–40 |
| 字色 | `--color` | 白/黄/青/绿/粉/橙 |
| 描边 | `--outline` | 无 / 细 / 粗 |
| 位置 | `--pos` | 贴近进度条 / 居中偏下 / 偏上 |
| 显示 | `--mode` | 中日双语 / 只看中文 / 只看日文 |
| 模型 | `--model` | 标准 9B（默认）/ 轻量 3B |
| 背景 | `--alpha` | 25%–100% |
| 淡入淡出 | `--no-fade` | 勾掉即关 |
| 高分屏放大 | `--no-scale` | 字号跟随屏幕高度（1080p 为基准） |

- 设置存 `JaSubs.settings`，下次打开自动载入；「恢复默认」一键还原；
- 「设备关键字」留空 = 跟随默认输出（推荐）；填 `Steam` 之类可强制某个设备；
- 字幕条本身仍可临时微调：拖动移动、滚轮字号、Ctrl+滚轮宽度、右键菜单（含位置/显示子菜单）；
  **右上角 ✕ 保留**，点一下就退；
- 托盘图标右键可开始/停止/退出；关窗口即停；
- 输出全部写到 `logs/gui.log`，点「看日志」直接打开。

图标是脚本生成的（`tools/gen_icon.py` 手写 ICO，不依赖 Pillow）：圆角蓝底 + 两条白色字幕线。

（ReazonSpeech 模型 777MB），翻译模型在 Ollama 里（6.6GB）。想拷给别人用，得连这些一起拷。
真要单文件得用 PyInstaller 打包，而本机 pip/uv 都被沙箱拒（见第二节），
需要用 PyPI JSON 手工解 wheel 的方式装齐 pyinstaller 及其依赖再试。
